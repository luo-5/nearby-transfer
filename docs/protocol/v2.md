# Nearby Transfer protocol v2

> Status: **foundation contract**. Version 2 is intentionally incompatible with
> the v0.x single-file protocol. Discovery, pairing, transfer manifests, chunk
> exchange, and file-library sessions will all use this version number.

## Scope and transport

Protocol v2 is a LAN-only application protocol. UDP discovery is only a hint
that a device may be reachable; it is never authorization. Any operation that
reads or writes user files requires a previously paired device identity and an
authenticated session over the selected transport.

All control messages are UTF-8 JSON. All messages include:

```json
{
  "app": "nearby-transfer",
  "protocolVersion": 2,
  "type": "message-type"
}
```

A recipient must reject a message when the application ID, version, type,
field type, bounds, signature, or peer identity does not match its expected
contract. Unknown fields may be ignored only after the signed/authorized
message schema explicitly permits extensions.

## Canonical JSON for signatures

Signatures use the restricted canonical JSON format implemented in:

- desktop: `src/v2/canonical-json.js`;
- Android: `ProtocolV2.canonicalJson`.

Rules:

1. Objects use lexicographically sorted Unicode-code-unit keys.
2. Arrays keep their existing order.
3. Only `null`, booleans, strings, arrays, plain objects, and safe integer
   values are allowed. Floats, exponent notation, `undefined`, binary values,
   and non-finite values are invalid.
4. Strings are UTF-8 JSON strings. Unpaired UTF-16 surrogates are invalid.
5. No whitespace is emitted outside JSON strings.

This removes implementation-specific object-property ordering from signed
payloads. The shared fixture is `test/fixtures/protocol-v2-pairing.json`; both
Node and Android JVM tests must pass it unchanged.

## Device identity

Every device has a long-lived Ed25519 signing key and X25519 key-agreement
key. Its public identity has the fields below:

```json
{
  "deviceId": "first 16 lowercase SHA-256 hex characters of signingPublicKey",
  "deviceName": "up to 128 non-blank characters",
  "fingerprint": "six uppercase SHA-256 groups of the signing public key",
  "signingPublicKey": "Ed25519 SPKI PEM",
  "encryptionPublicKey": "X25519 SPKI PEM"
}
```

The receiver recomputes `deviceId` and `fingerprint`, parses both PEM keys, and
rejects a mismatched type or identity. A device identity change invalidates all
trust records and requires a new pairing.

## Pairing

1. The initiator creates a random 16-byte base64url `pairingId` and sends a
   signed `pairing-offer` through discovery or QR bootstrap.
2. The responder validates the offer, replies with its own signed identity, and
   both sides derive the same six-digit comparison code from the complete,
   role-ordered identity transcript.
3. Both users explicitly confirm the displayed code. A mismatch, timeout,
   cancellation, or signature failure rejects the pairing.
4. Only after both confirmations are signed and stored is the peer trusted.

The code transcript is canonical JSON of:

```json
{
  "app": "nearby-transfer",
  "protocolVersion": 2,
  "type": "pairing-code",
  "pairingId": "base64url-encoded 16 bytes",
  "initiator": { "public identity": "..." },
  "responder": { "public identity": "..." }
}
```

The six-digit code is `uint32be(SHA-256("nearby-transfer/v2/pairing-code\\0" || transcript)[0..3]) mod 1,000,000`, zero-padded. It is a short
authentication string: users must compare it on both devices before trusting
the peer. It is not a password and is never stored as a credential.

A `pairing-offer` is canonical-signed with the initiator's Ed25519 key over:

```json
{
  "app": "nearby-transfer",
  "protocolVersion": 2,
  "type": "pairing-offer",
  "pairingId": "...",
  "issuedAt": 1760000000000,
  "identity": { "public identity": "..." },
  "capabilities": ["file-library", "transfer"]
}
```

Capabilities are lower-case ASCII tokens, de-duplicated and sorted before
signing. Pairing offers must be short lived; the final timeout window will be
implemented with the transport/session service.

## Planned authenticated message families

The following names are reserved now so desktop and Android can evolve without
another incompatible rename:

- `discovery-announce`
- `pairing-offer`, `pairing-confirm`, `pairing-cancel`
- `transfer-manifest`, `transfer-chunk`, `transfer-complete`
- `library-session`

Their transport framing, authorization, expiry, and storage schemas will be
added alongside each implementation phase. They must never be accepted from an
unpaired peer except for the pairing bootstrap messages.

## Migration from v0.x

v0.x discovery and transfer requests use protocol version `1`. v1.0 clients
must advertise and accept version `2` only. Existing local identity material
and device names can be retained, but every existing peer must be paired again.
No downgrade or mixed-version transfer path is provided.

## Transfer manifests

A v2 transfer always starts with a complete `transfer-manifest` before file
bytes are accepted. The manifest is both the durable transfer-job input and the
basis for the receiver's approval UI. It has this exact schema; unknown fields
are rejected.

```json
{
  "app": "nearby-transfer",
  "protocolVersion": 2,
  "type": "transfer-manifest",
  "taskId": "base64url-encoded 16 random bytes",
  "conflictStrategy": "auto-rename",
  "entries": [
    { "kind": "directory", "path": "资料/项目" },
    {
      "kind": "file",
      "path": "资料/项目/说明.txt",
      "size": 12,
      "sha256": "64 lowercase hexadecimal SHA-256 characters"
    }
  ],
  "totalFiles": 1,
  "totalBytes": 12
}
```

`taskId` is exactly 16 random bytes encoded with unpadded base64url. The
conflict strategy is intentionally fixed to `auto-rename`: a receiver must
never overwrite an existing path. The receive implementation chooses a safe,
unique destination name after the user has approved the manifest.

Paths always use relative POSIX separators, even on Windows. A path must be
non-empty; may not be absolute, contain `.` or `..`, backslashes, NUL/control
characters, or Windows-invalid characters; and may not use a Windows reserved
device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1` through `COM9`, or `LPT1`
through `LPT9`, including extensions and Windows-compatible superscript variants). Components may not end in a period or
space. The manifest rejects case-insensitive Windows path collisions and
requires every declared nested directory and every file parent directory to be declared explicitly. Empty
directory declarations are therefore preserved.

Each file declares a non-negative safe-integer byte size (at most 1 TiB) and a
lowercase hexadecimal SHA-256 digest. A manifest contains at most 10,000 total
entries, 8,192 files, and 4 TiB of file data. `totalFiles` and `totalBytes` are
verified computed values, not sender-controlled summaries.

Desktop persistence uses the canonical JSON encoder described above. When a
serialized manifest is read back, it is revalidated and rejected unless its
stored bytes exactly equal the canonical form. This prevents multiple textual
representations of the same durable job and makes subsequent signing/session
work deterministic. The reference desktop module is
`src/v2/transfer-manifest.js`.
